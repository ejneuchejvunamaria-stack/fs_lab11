## Задание 2. Исследование файловой системы виртуальной машины

**Гипотеза:**
Корневая файловая система не обязательно должна быть на /dev/sda1 (она может быть на любом разделе, например /dev/sda2). В Linux может быть несколько смонтированных файловых систем одновременно. /proc не является обычным каталогом на диске, это виртуальная ФС.

**Эксперимент:**
Выполнены команды: `lsblk -f`, `df -hT -x squashfs`, `findmnt /`, `findmnt /proc`, `findmnt /sys`.

**Наблюдение:**
1. Корневая ФС смонтирована на устройстве `/dev/sda2` (тип ext4).
2. Свободное место на корневой ФС составляет около 10-15 ГБ (зависит от настроек ВМ).
3. Файловая система `/proc` имеет тип `proc`, а `/sys` — `sysfs`. Они не занимают места на диске.

**Вывод:**
В Linux используется единое дерево каталогов. Виртуальные файловые системы (proc, sysfs, tmpfs) создаются ядром в оперативной памяти для предоставления интерфейса к оборудованию и процессам, поэтому они не являются обычными дисковыми каталогами.

## Задание 3. Исследование «Файл переименовали — изменился ли он?»

**Гипотеза:**
При переименовании файла в пределах одной файловой системы номер inode не изменится, содержимое останется прежним, а блоки данных не будут скопированы.

**Эксперимент:**
Выполнены команды: `echo "Hello" > report.txt`, `stat report.txt`, `mv report.txt final.txt`, `stat final.txt`. Дополнительно создан пустой файл `touch empty.txt` и проверен через `stat`.

**Наблюдение:**
Номер Inode у файла `report.txt` и `final.txt` совпадает (например, 123456). В выводе `stat` для пустого файла логический размер (Size) равен 0, но выделенное пространство (Blocks) также равно 0, либо занимает 1 блок (4 КБ) в зависимости от ФС.

**Вывод:**
Переименование в Linux — это просто изменение записи в каталоге (имени файла). Сам inode и блоки данных остаются нетронутыми, поэтому файл не копируется и не меняет свое физическое расположение. Логический размер (Size) показывает, сколько байт в файле, а Blocks — сколько физических блоков на диске выделено (они могут отличаться из-за округления до размера блока).

## Задание 4. Кейс «Исчезнувший отчет»

**Наблюдения:**
При создании жесткой ссылки (`ln`) файлы `report.txt` и `backup.txt` получили одинаковый inode (131334). У символической ссылки (`shortcut.txt`) inode свой (131336).
После удаления `report.txt` жесткая ссылка `backup.txt` продолжила работать и данные остались доступны. Символическая ссылка `shortcut.txt` стала «битой» и выдала ошибку, так как указывала на несуществующий путь.
После команды `git restore` файл `report.txt` восстановился с новым inode (131347). Символическая ссылка снова заработала (так как имя файла совпало), но жесткая связь с `backup.txt` была потеряна (inode стали разными).
Чтобы восстановить жесткую связь, пришлось удалить файл, созданный Git, и создать его заново командой `ln` от `backup.txt`. Теперь у них снова одинаковый inode (131334).

**Вывод:**
Git сохраняет содержимое файлов и символические ссылки, но не сохраняет отношения жестких ссылок (так как для Git это просто два независимых файла). Жесткая ссылка указывает на inode, а символическая — на путь (имя) файла.

## Задание 6. Кейс «Почему один файл сохранился, а другой исчез?»

**Наблюдения:**
При работе с ext4 (виртуальный диск `disk.img`) файл `note.txt` успешно сохранился после размонтирования и повторного монтирования.
При работе с tmpfs файл `note.txt` исчез сразу после размонтирования (папка стала пустой).

**Объяснение результатов:**
1. В ext4 данные хранятся на блочном устройстве (в файле `disk.img`), поэтому они никуда не исчезают при отключении. Размер доступного пространства меньше 50 МБ, потому что часть места занимает служебная информация файловой системы (суперблок, таблица inode, журнал).
2. В tmpfs данные хранятся в оперативной памяти (и swap). При размонтировании эта память освобождается, и данные удаляются.
3. Точка монтирования — это каталог, через который предоставляется доступ к файлам подключенной файловой системы.
4. Если процесс использует файл на диске, система не даст его размонтировать (выдаст ошибку `device is busy`), пока процесс не завершится.
5. Если удалить `disk.img`, пока он смонтирован, для системы это не будет проблемой — она продолжит работать с ним, так как файл уже открыт. Данные сохранятся, но после размонтирования файл будет потерян, так как его физически удалили с диска.

## Часть IV. Ответы на контрольные вопросы

1. **Чем имя файла отличается от inode?** Имя файла — это запись в каталоге, понятная человеку (например, `report.txt`). Inode — это уникальный номер в файловой системе, содержащий метаданные (права, размер, ссылки на блоки данных).
2. **Почему после mv номер inode обычно остаётся прежним?** Потому что `mv` в пределах одной файловой системы не копирует данные, а просто меняет имя файла в каталоге. Сам inode и блоки данных не меняются.
3. **Почему два файла могут иметь одинаковый inode?** Потому что это жесткие ссылки. Они указывают на один и тот же inode и одни и те же данные, просто имеют разные имена в каталоге.
4. **Почему после git restore жесткая связь не восстанавливается автоматически?** Git не хранит информацию о жестких ссылках. Для него это два независимых файла с одинаковым содержимым. При восстановлении он создает новый файл (с новым inode).
5. **Почему символическая ссылка может стать битой?** Потому что она хранит не inode, а путь (имя) целевого файла. Если файл удалить или переименовать, ссылка не сможет найти его по указанному пути.
6. **Почему файл нельзя запустить, даже если его содержимое корректно?** Потому что у файла нет права на выполнение (`x`) для текущего пользователя.
7. **Какие права нужны для удаления файла из каталога?** Нужны права на запись (`w`) и выполнение (`x`) на сам родительский каталог, а не на сам файл.
8. **Что означает chmod 750?** Владелец получает полные права (`rwx` = 7), группа получает чтение и выполнение (`r-x` = 5), остальные не получают никаких прав (`---` = 0).
9. **Почему ext4 сохраняет данные после размонтирования, а tmpfs — нет?** ext4 хранит данные на физическом (или виртуальном) диске. tmpfs хранит данные в оперативной памяти, которая очищается при размонтировании.
10. **Почему номер inode недостаточен для однозначного определения файла?** Номер inode уникален только в пределах одной файловой системы. В другой файловой системе может быть файл с таким же inode.
11. **Что произойдёт с удалённым файлом, если процесс продолжает держать его открытым?** Файл исчезнет из каталога, но данные (блоки на диске) не будут освобождены, пока процесс не закроет файл.
12. **Почему Git не должен содержать secret.txt и disk.img?** `secret.txt` может содержать пароли (утечка безопасности), а `disk.img` — это большой бинарный файл, который раздувает репозиторий. Такие файлы добавляют в `.gitignore`.
